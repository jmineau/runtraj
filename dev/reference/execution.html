Execution#

Most users only need project.run(), project.submit(), or runtraj run (Running). The functions below do the work underneath.

  • run() is what project.run() calls. It finds the releases with missing results, runs them, and waits until they finish. task=(i, n) runs share i of n here (task_share()), which is what runtraj run --task i/n does.

  • submit() is what project.submit() calls. It writes a job array script (job_script()) whose tasks each run runtraj run --task, submits it with sbatch, and returns the job id at once. With backend: kubernetes it makes an indexed Job instead (job_manifest()) and creates it with kubectl.

  • schedule_job() is what runtraj schedule calls: a CronJob (cron_job_manifest()) whose pod each hour runs runtraj tick, which adds the hours now due (add_due_releases()) and runs them.

  • run_result() runs the transport model for one Simulation and writes its particles and log.

  • run_stages() runs the stages of the variants that share those particles: each stage file that is missing, in the order the stages read one another, and each again when what it reads was made again. run_stage() runs one, which writes its own file.

  • run_release() runs every variant of one release, skipping what exists. Variants that share particles run the transport model once and run their stages on the particles in memory. A failure is recorded with the simulation (runtraj.Simulation.failure). Workers are always handed releases.

  • run_releases() runs a list of releases, in this process or in a process pool.

On Slurm each task of the job array runs one share of the releases (task_share()) with runtraj run --task. A local run happens in this process. A program that starts the tasks itself, on another scheduler, writes pending() to the releases.txt each task reads (runtraj run --releases; On Any Scheduler); wait() waits for a Slurm job array by its id.

Backends#

Where the releases run is a backend, which execution.backend names: local runs them in this process, slurm as one Slurm job array, pbs as one PBS job array, kubernetes as one Kubernetes indexed Job. Each is a Backend, and its block under execution is its config_class, a BackendConfig. run() and submit() find it with get_backend() and hand it the releases whose results are missing.

A scheduler runtraj does not have can be a backend in a package of your own, named by the import path of its class, as a transport model or a stage is:

execution:
  backend: mypkg.backends.QueueBackend
  myqueue:            # the class's name
    queue: short
    cpus: 4

Its submit() starts the tasks, each of which runs runtraj run <project> --task i/N with i from the scheduler ($SLURM_ARRAY_TASK_ID in a Slurm array), and returns what names them. A backend that sets waits and writes run() waits for them, so runtraj run can use it; one that writes jobs() lists them in runtraj status. The tasks need nothing else: every task splits the releases the same way (pending()), skips what is complete, and exits with a code that says whether to try it again (Exit codes).

runtraj.execution.BackendConfig

runtraj.execution.get_backend

Return the backend name names.

runtraj.execution.runner.LocalBackend

The local backend: the releases run here, in this process, cpus at a time.

runtraj.execution.slurm.SlurmBackend

The slurm backend: the releases as the tasks of one Slurm job array (submit_array()).

runtraj.execution.pbs.PbsBackend

The pbs backend: the releases as the subjobs of one PBS job array (submit_array()).

The kubernetes backend: the releases as the pods of one indexed Job (submit_job()).

Slurm job arrays#

The Slurm backend is runtraj.execution.slurm: it writes the job array and fetch scripts, submits them with sbatch, follows the tasks with sacct. The job array script requeues a task that Slurm stops near its time limit or preempts; the worker only stops, and exits with 3.

runtraj.execution.job_script

Return the sbatch script of a job array whose tasks each run a share of the releases.

runtraj.execution.fetch_script

Return the sbatch script of the job that gets the met files before a job array.

runtraj.execution.slurm.submit_array

Write a submission folder for pending releases, submit its job array, and return its job id and cluster.

PBS job arrays#

The PBS backend is runtraj.execution.pbs: it writes the job array script, submits it with qsub, and follows it with qstat.

Transport model#

The worker runs a simulation through the transport model its settings name. runtraj supports HYSPLIT (HYSPLIT Integration) and FLEXPART 11 (FLEXPART Integration), and has no default: config.yaml names the model in its models block. CONTRIBUTING describes how to add another, named by its import path. A model fails a run that its meteorology does not cover, as MET_COVERAGE. Particles that all leave the met’s domain before the end of the run are a complete run. Use check_model() in the tests of a model of your own.

Stages#

A stage makes one file per release from a simulation’s results, after the transport model runs. PYSTILT’s footprint is one (stilt.footprint.FootprintStage). A stages block of config.yaml names its stage’s class by import path, so a stage in a package of your own needs no registration, and CONTRIBUTING describes how to write one. In its tests, check_stage() checks its settings record, and run_stage() runs it end to end in a project of one release, on particles you give it and with no transport model installed (ReplayModel).
